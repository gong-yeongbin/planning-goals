# /goal 은 어떻게 판정하나

출처: https://code.claude.com/docs/en/goal.md (2026-09 기준). 계획 파일을 설계할 때 이 동작에 맞춰야 평가 모델이 판정할 수 있다.

## 판정 흐름

1. `/goal <조건>` 을 치면 조건 자체가 첫 지시가 되어 Claude 가 턴을 시작한다.
2. 턴이 끝날 때마다 Claude Code 가 조건과 지금까지의 대화를 작은 모델(기본 Haiku)에 보낸다.
3. 평가 모델은 세 가지 중 하나를 이유와 함께 돌려준다.
   - 미충족: Claude 가 그 이유를 지침 삼아 다음 턴을 계속한다.
   - 충족: goal 이 해제되고 달성 기록이 남는다.
   - 불가능: goal 이 해제되고 실패 기록이 남는다.

## 평가 모델이 할 수 없는 것

- 도구를 못 쓴다. 명령을 실행하지 않고 파일을 읽지 않는다. Claude 가 대화에 드러낸 것만 본다.
- 그래서 "테스트 통과" 는 Claude 가 테스트를 실행해 출력을 대화에 남겼을 때만 판정된다. 파일 안의 `[x]` 표시도 Claude 가 파일을 고치는 편집이 대화에 보여야 한다.

## 제한

- 조건은 4,000자 이하.
- Claude 가 도구 호출 없이 몇 턴 연속으로 말만 하면 루프가 멈추고 제어가 사용자에게 돌아간다.
- 서브에이전트나 백그라운드 명령이 돌고 있으면 그 턴의 평가는 건너뛴다.
- 세션당 활성 goal 은 하나. 새 `/goal` 은 이전 것을 대체한다. 구현 goal 과 TEST goal 을 순서대로 따로 입력하는 이유다.
- 턴 수를 제한하려면 조건에 `또는 N턴 후 중단` 같은 절을 넣는다.

## 좋은 조건의 세 요소 (공식 문서)

- 측정 가능한 끝 상태 하나: 테스트 결과, 빌드 종료 코드, 파일 수, 빈 큐
- 증명 방법: "`npm test` 가 0 으로 종료", "`git status` 가 깨끗함"
- 지켜야 할 제약: "다른 테스트 파일은 수정하지 않음"

이 스킬은 세 요소를 조건문이 아니라 파일의 단계·DoD·제약 절에 두고, 조건문은 그 파일을 가리키게 한다.
